# REQ-06 — Agent-run builds prefixed with `NO_DNA=1`

## Requirement (verbatim)

> Agent-run builds: prefix `NO_DNA=1` (`NO_DNA=1 anchor build`, `NO_DNA=1 anchor test`).

— `/home/david/claude/thugbirdz/IMPLEMENTATION_APPENDIX.md` §1, line 33.

Holds-if criterion supplied with the requirement: "Build/test scripts invoked by agents
set NO_DNA=1".

## Verdict

**partial** — confidence **medium**.

## What the requirement demands

This is an operational directive, not program logic: whenever an agent runs a build or
test, the `NO_DNA=1` environment variable must be set on the invocation. It can be
satisfied two ways: (a) mechanically, by committed build/test scripts (shell wrappers,
`Anchor.toml [scripts]`, a `.cargo/config.toml [env]` block, CI) that set the variable
themselves, or (b) by instruction, if every channel through which an agent learns how to
build tells it to prefix `NO_DNA=1`. The holds-if criterion names (a); the requirement's
own wording ("prefix") describes (b).

## Where mechanical enforcement is missing (scripts — absent)

The repo contains exactly one committed, machine-executed build/test script, and it does
**not** set the variable:

- `/home/david/claude/thugbirdz/program/Anchor.toml`, `[scripts]` section:

  This is what `anchor test` executes. It does not embed `NO_DNA=1`, so a bare
  `anchor test` runs `cargo test` without the variable. (If the agent obeys the docs and
  types `NO_DNA=1 anchor test`, the env var propagates to the child `cargo test`, so the
  embedded script does not undo the prefix — it just does not supply it.)

## Why this verdict and not the adjacent ones

- Not **implemented**: the holds-if criterion asks that build/test *scripts* set
  `NO_DNA=1`. The one committed script that agents' builds flow through
  (`Anchor.toml [scripts] test`) does not set it, and no wrapper, cargo `[env]`, hook, or
  CI file sets it anywhere. Compliance currently depends entirely on the agent reading and
  obeying prose.
- Not **absent**: the directive is genuinely propagated at every entry point an agent
  would touch — CLAUDE.md (the agent-instruction channel), the README's only build
  commands, and both test-file headers — and the appendix's own wording ("prefix") frames
  it as an invocation convention rather than a script property. An agent following the
  repo's documented commands does run `NO_DNA=1` builds.
- Not **undecidable**: the check is concrete (does anything set NO_DNA=1 on agent builds)
  even though the variable's purpose is undocumented.

So: holds on the path where the agent follows the documented commands; does not hold on
the path where an agent (or the Anchor toolchain itself) invokes `anchor test` /
`cargo test` directly, because no script supplies the variable. That split is "partial".

## Open questions

- What `NO_DNA` actually gates is defined nowhere in the repo or in the visible machine
  config (no consumer found in shell rc files, cargo config, or Claude settings). Without
  knowing the consumer, one cannot say whether an unprefixed build merely loses a
  convenience or produces a wrong artifact.
- `Anchor.toml`'s script could trivially embed the prefix
  (`test = "NO_DNA=1 cargo test --features test-keys"`), which would convert this to
  mechanical enforcement for the `anchor test` path.
