# REQ-07 — Gate 6 uses verifiedBuild/OtterSec, not a hand-rolled hash comparison

## Requirement (verbatim)

From `/home/david/claude/thugbirdz/IMPLEMENTATION_APPENDIX.md` §1, "Verifiable builds — adopt this" (L35–L42):

> Anchor 1.1.x supports `verifiedBuild` via OtterSec (`verify.osec.io`). Gate 6 currently
> hand-rolls "on-chain hash matches a local build".
>
> Use the standard mechanism instead. It makes the program **publicly verifiable by anyone**,
> not just by us — which is the same argument that chose PDAs over merkle.

Holds if: Gate 6 uses Anchor's verifiedBuild/OtterSec mechanism rather than a hand-rolled hash comparison.

## Verdict

**partial** — confidence: medium.

The negative half (no hand-rolled hash comparison anywhere in the repo) is verifiable and
holds. The positive half (Gate 6 actually *uses* verifiedBuild) exists only as committed
process documentation: Gate 6 is a Phase 6 mainnet-deploy step that has not been executed,
and no script, CI job, or config in the repo invokes the OtterSec/verifiedBuild mechanism.

## What the requirement demands

This is a process/tooling requirement, not an on-chain one. An implementation satisfies it
when the Gate 6 bytecode-verification step is defined and performed via the standard
Anchor/OtterSec verified-build mechanism, and when no hand-rolled "hash the on-chain
program, compare to a local build" script stands in for it.

## What is missing (why not "implemented")

- Gate 6 has not been executed: README L30 says mainnet deploy comes "at Phase 6", and the
  Gate status section (README L58–L64) lists only Gates 1–2, both still open items.
- Nothing executable in the repo performs or scaffolds the verifiedBuild check: no
  `solana-verify`, `anchor verify`, `verify-from-repo`, or `osec` invocation exists outside
  prose (search record below); there is no CI workflow at all in the project
  (no `.github/` at the repo root).
- So "Gate 6 uses verifiedBuild" is a commitment every document makes consistently, but the
  code cannot yet demonstrate it; only the absence of the forbidden alternative is
  demonstrable.

## Why this verdict and not the adjacent ones

- Not **implemented**: "implemented" requires reading the enforcement. There is no
  executable enforcement — Gate 6 is unexecuted and untooled; the verifiedBuild adoption
  lives in plan text. A future operator could still hand-roll a hash check at deploy time
  with nothing in the repo stopping them.
- Not **contradicted**: the appendix's "Gate 6 currently hand-rolls" describes a superseded
  draft state; the current IMPLEMENTATION_PLAN.md Phase 6 text uses verifiedBuild, and no
  hash-comparison artifact survives anywhere (search record above).
- Not **absent**: the requirement is visibly acted on — the plan was revised to the standard
  mechanism, every Gate 6 reference in README/SECURITY_CHECKLIST/appendix names
  verifiedBuild, and the shipped script explicitly scopes itself below Gate 6.

## Open questions

- Whether Gate 6, when run at Phase 6, will be recorded (e.g. a verify.osec.io link or
  `solana-verify` output committed to the repo). Nothing currently reserves a place for
  that evidence.
- Gate 1 (byte-identical rebuild on a second machine) is stated as "finally proven by
  verifiedBuild at Gate 6" (README L60–L61) — the two gates are coupled, so a Gate 6 that
  slips back to a local hash comparison would silently weaken Gate 1 as well.
