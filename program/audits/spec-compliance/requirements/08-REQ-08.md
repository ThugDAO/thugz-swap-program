Holds if: the Pool account has exactly these fields in this order; serialized size is

## Verdict

**implemented** — confidence **high**.

## What the requirement demands

1. A `Pool` account struct with exactly twelve fields, in the exact order and with the
   exact types listed (2×`Pubkey`, 4×`u16`, 2×`bool`, 1×`i64`, 3×`u8`).
2. A serialized on-chain size of 93 bytes: 8-byte Anchor discriminator + 85 bytes of
   Borsh-encoded field data.

## Where enforcement lives

`program/programs/thugz-swap/src/state.rs` L8–L23:

```rust
#[account]
#[derive(InitSpace)]
pub struct Pool {
    pub admin: Pubkey,
    pub collection: Pubkey,
    pub expected: u16,
    pub deposited: u16,
    pub swapped: u16,
    pub recovered: u16,
    pub sealed: bool,
    pub paused: bool,
    pub unlock_ts: i64,
    pub bump: u8,
    pub vault_bump: u8,
    pub treasury_bump: u8,
}
```

- **Field match**: all twelve fields, same names, same types, same order as the spec.
  No extra fields, none missing. The doc comment at state.rs L3 restates the size
  claim: "8 discriminator + 85 = 93 bytes."
- **Size**: Anchor's `#[account]` serializes with Borsh in declaration order, with
  fixed sizes: `Pubkey`=32, `u16`=2, `bool`=1, `i64`=8, `u8`=1. Sum:
  32+32+2+2+2+2+1+1+8+1+1+1 = 85; +8 discriminator = 93. The layout has no
  variable-size types (no `String`/`Vec`), so the serialized size is a compile-time
  constant of the type itself.
- **Allocation uses the same number**: `program/programs/thugz-swap/src/instructions/initialize_pool.rs` L22
  allocates `space = 8 + Pool::INIT_SPACE` inside the `#[account(init, ...)]`
  attribute. `#[derive(InitSpace)]` (state.rs L9) computes `INIT_SPACE` = 85 from the
  same field list, so the account is created with exactly 93 bytes. Since the account
  is `init` (not `init_if_needed`, not zero-copy with slack), the on-chain data length
  is exactly 93.

## Paths walked

- `initialize_pool` is the only place a Pool account is created
  (`initialize_pool.rs` L19–L26, the sole `init` of `Account<'info, Pool>` in the
  program — confirmed by the grep over `src/` below). Every later instruction
  deserializes the same 93-byte layout via `Account<'info, Pool>`; Anchor's Borsh
  round-trip fails if the layout diverged, so there is no path with a different
  layout.
- No `realloc` on the Pool anywhere (see search log), so the size cannot change
  post-init.

## Why this verdict and not the adjacent one

- Not **partial**: the layout is a single type definition; there is no path-dependent
  variant. All instructions share the one struct.
- Not **stronger-than-spec**: the code adds nothing beyond the spec's layout; the
  requirement is met exactly, not exceeded.
- The absence of an explicit `assert_eq!(8 + Pool::INIT_SPACE, 93)` test does not
  weaken the verdict to partial: the requirement is about the layout and size, both
  of which follow deterministically from the type definition and the fixed-size Borsh
  encoding, and the allocation site uses the derived constant rather than a hand-typed
  number (so it cannot drift from the struct).
