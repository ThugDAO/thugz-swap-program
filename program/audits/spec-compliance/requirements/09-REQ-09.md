# REQ-09 — Mapping account layout (82 bytes incl. discriminator)

"// 8 discriminator + 74 = 82"

Holds if: the Mapping account has exactly these fields in this order; serialized size is 82 bytes including the discriminator.

## Verdict

**implemented** — confidence **high**.

## What the requirement demands

1. A `Mapping` account struct with exactly five fields — `new_mint: Pubkey`, `claimed: bool`, `claimed_by: Pubkey`, `claimed_at: i64`, `bump: u8` — in that order (Borsh serializes fields in declaration order, so order is layout).
2. Every on-chain allocation of the account sized at 8 (Anchor discriminator) + 74 (32+1+32+8+1) = 82 bytes.

## Where it lives

### The struct — `program/programs/thugz-swap/src/state.rs` L32–L41

```rust
#[account]
#[derive(InitSpace)]
pub struct Mapping {
    pub new_mint: Pubkey,
    pub claimed: bool,
    pub claimed_by: Pubkey,
    pub claimed_at: i64,
    pub bump: u8,
}
```

Field-for-field, order-for-order identical to the appendix. No extra fields, none missing. The doc comment above it (state.rs L25) repeats the size claim: "8 discriminator + 74 = 82 bytes."

`#[derive(InitSpace)]` makes Anchor compute `Mapping::INIT_SPACE` from the field types: `Pubkey` = 32, `bool` = 1, `Pubkey` = 32, `i64` = 8, `u8` = 1 → 74. All five types are fixed-size primitives with no `#[max_len]` involvement, so the derived value is exactly the sum — 74.

### The allocation — `program/programs/thugz-swap/src/instructions/deposit_bird.rs` L84, L121

The Mapping is created only in `deposit_bird`, via the manual allocate/assign path (no Anchor `init`):

```rust
let space = 8 + Mapping::INIT_SPACE;          // L84 → 8 + 74 = 82
let required = Rent::get()?.minimum_balance(space);   // L85
...
system_program::allocate(..., space as u64)?;  // L110–L122, allocates 82 bytes
```

followed by `system_program::assign` to `crate::ID` (L123–L132) and an explicit full-struct write:

```rust
let state = Mapping { new_mint: new_mint_key, claimed: false,
                      claimed_by: Pubkey::default(), claimed_at: 0,
                      bump: mapping_bump };       // L135–L141
state.try_serialize(&mut &mut data[..])?;         // L143
```

`try_serialize` (Anchor `#[account]` impl) writes the 8-byte discriminator followed by Borsh-serialized fields in declaration order — 82 bytes total into the 82-byte buffer. An oversized struct would make this line fail at runtime; an undersized allocation would too.

### Readers

`Box<Account<'info, Mapping>>` in `swap.rs` L37, `fix_mapping.rs` L29, `recover.rs` L27 — all deserialize through the same Anchor impl of the same struct, so there is exactly one layout in the program.

## Paths walked

- `deposit_bird` is the sole creation path (grep for `Mapping::INIT_SPACE` and `allocate` hits only deposit_bird.rs); it allocates 82 and serializes the full struct. Enforced.
- `swap` mutates only `claimed`/`claimed_by`/`claimed_at` through the typed `Account<Mapping>`; no realloc anywhere (grep `realloc` → 0 hits in src/). Layout cannot drift post-init.

## Why this verdict and not the adjacent ones

- Not **partial**: there is exactly one creation site, and it derives the size from the struct itself (`8 + Mapping::INIT_SPACE`), so struct and allocation cannot disagree. All readers share the one struct.
- Not **stronger-than-spec**: the code adds nothing beyond the appendix layout (the init-once guard etc. belong to other requirements).
- The 82 figure is not asserted by a literal constant or a test (`const _: () = assert!(Mapping::INIT_SPACE == 74)` would pin it), but the requirement asks that the size *be* 82, not that a test assert it — and with five fixed-size primitive fields, `INIT_SPACE` = 74 is a compile-time certainty of the derive.

## Open questions

None material. A compile-time size assertion or a level-1 test checking `account.data.len() == 82` would make the 82 regression-proof against future field additions, but its absence does not break the requirement today.
