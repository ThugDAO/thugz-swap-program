# REQ-11 — The rent payer cannot be Pool

## Requirement (verbatim)

From `/home/david/claude/thugbirdz/IMPLEMENTATION_APPENDIX.md` §2:

> "`system_program::create_account` requires its funding account to be **system-owned with no data**. `Pool` carries data, so it can never be the payer for Mapping init or ATA creation."

Holds if: no code path uses the Pool PDA as the funding/payer account for `create_account` or ATA creation.

## Verdict

**implemented** — confidence **high**.

## What the requirement demands

Every rent-funding site in the program — Mapping account creation and every ATA creation — must draw lamports from something other than the Pool PDA. The spec's chosen payer is the system-owned, zero-data treasury PDA; the invariant to check is the negative one: Pool never appears as `payer`/`from` in any account-creation flow, including Anchor `init` constraints and explicit CPIs.

## Where enforcement lives

There are exactly three kinds of account creation in the program, and none uses Pool as payer.

### 1. ATA creation — single funnel, treasury pays

All ATA creation goes through one helper, `create_ata_idempotent_treasury_pays` in `program/programs/thugz-swap/src/instructions/mod.rs` (L35–L58). Its payer is hard-wired to the treasury parameter, typed `SystemAccount` (so Anchor rejects a data-bearing account in that slot at deserialization):

```rust
pub(crate) fn create_ata_idempotent_treasury_pays<'info>(
    treasury: &SystemAccount<'info>,
    ...
    associated_token::create_idempotent(CpiContext::new_with_signer(
        AssociatedToken::id(),
        associated_token::Create {
            payer: treasury.to_account_info(),   // mod.rs L48
            ...
        },
        &[seeds],  // seeds = [TREASURY_SEED, treasury_bump]  (L44)
    ))
```

All five call sites pass `&ctx.accounts.treasury` as the first argument, and in each Accounts struct `treasury` is `#[account(mut, seeds = [TREASURY_SEED], bump = pool.treasury_bump)] pub treasury: SystemAccount<'info>`:

- `swap.rs` L103 (vault_original_ata) and L112 (holder_new_ata)
- `deposit_bird.rs` L154 (vault_ata); treasury account declared at deposit_bird.rs L58–L59
- `recover.rs` L81 (custodian_ata)
- `fix_mapping.rs` L81 (custodian_ata)

### 2. Mapping init — no `create_account` at all; deficit funded by treasury

`deposit_bird.rs` L75–L133 does the appendix-§4 manual init. Rent is topped up by a `system_program::transfer` whose `from` is the treasury, signed with treasury seeds (L91–L98):

```rust
// Transfer only the deficit from the TREASURY PDA (never Pool — a
// data-bearing account cannot fund account creation).
let treasury_seeds: &[&[u8]] = &[TREASURY_SEED, &[ctx.accounts.pool.treasury_bump]];
system_program::transfer(
    CpiContext::new_with_signer(
        System::id(),
        system_program::Transfer {
            from: ctx.accounts.treasury.to_account_info(),
            to: mapping_info.clone(),
        },
        ...
```

Then `allocate` (L113) and `assign` (L123) are signed by the Mapping PDA itself — neither takes a payer, so `create_account`'s funding-account constraint is never even engaged for the Mapping.

### 3. The one Anchor `init` in the program — Pool itself, paid by admin

`initialize_pool.rs` L19–L27: `#[account(init, payer = admin, ...)] pub pool: ...`. Pool is the account being created there, not the payer. The handler deliberately never touches the treasury (L38–L42 comment: it "must stay system-owned with zero data ... or it dies as a legal `create_account` payer").

## Paths walked

- swap → two ATA creations, both treasury-paid (swap.rs L103, L112).
- deposit_bird → Mapping rent transfer from treasury (L91), allocate/assign self-signed (L113, L123), vault ATA treasury-paid (L154).
- recover → custodian ATA treasury-paid (recover.rs L81).
- fix_mapping → custodian ATA treasury-paid (fix_mapping.rs L81); its `close = treasury` (noted at L115) moves lamports TO the treasury, not from Pool.
- initialize_pool → Anchor `init` of Pool with `payer = admin` (initialize_pool.rs L21).
- seal / set_paused → no account creation (no hits in the payer/init grep below).

## Searches

- `grep -rn "payer|create_account|create_associated" src/` → payer appears only in comments, in the helper (mod.rs L48, treasury), and in `payer = admin` (initialize_pool.rs L21). No `create_account` CPI call exists in the program — only doc-comment mentions.
- `grep -rn "create_ata_idempotent_treasury_pays|create_idempotent|payer\s*=|init_if_needed|#\[account(init"` → helper defined once (mod.rs L35), called 5 times (swap x2, deposit_bird, recover, fix_mapping); `init_if_needed` appears only in a comment explaining why it is NOT used (mod.rs L28); the only `#[account(init` is Pool in initialize_pool.rs.
- `grep -rn "pool.to_account_info|lamports"` → 0 hits of Pool used as an AccountInfo in any CPI; the only lamport reads are `mapping_info.lamports()` (deposit_bird.rs L86) and a comment in fix_mapping.rs L115. No manual lamport debit from Pool anywhere.

## Why this verdict and not the adjacent one

Not `partial`: every creation path was enumerated (the greps cover all seven instruction files) and each one funds from the treasury or admin — there is no branch where Pool is substituted. Not `stronger-than-spec`: the code enforces exactly the spec's payer model; the `SystemAccount` typing of treasury and the single-funnel helper are the mechanisms the appendix itself prescribes, not additions beyond it. The distinction from a name-only check: the helper's name claims treasury pays, and the body was read — `payer: treasury.to_account_info()` at mod.rs L48 with the treasury seeds as signer, and every caller passes the seeds-constrained treasury account.

## Open questions

None material. Note the requirement is enforced structurally (types + a single helper + no `create_account` call at all) rather than by a runtime `require!` on the payer key — which is the stronger form: there is no code through which a Pool-as-payer transaction could be expressed.
