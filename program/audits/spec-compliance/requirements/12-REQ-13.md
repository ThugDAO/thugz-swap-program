# REQ-13 — Closed-account rent returns to the treasury

## Requirement (verbatim)

From `/home/david/claude/thugbirdz/IMPLEMENTATION_APPENDIX.md` §2, "The rent payer cannot
be `Pool`" (line 99):

> Use a separate **`["treasury"]` PDA, system-owned, zero data**, which signs as payer via
> seeds. Closed-account rent returns there.

Reinforced later in the same document, "Closing in `fix_mapping`" (lines 228–232):

> Rent returns to the **treasury**, not the pool and not the admin. Note that runtime `close`
> *can* credit a data-bearing account — it is not `create_account` — so `close = pool` would
> compile happily and silently disagree with the payer model.

Holds if: lamports from closed accounts are credited to the treasury PDA.

## Verdict

**implemented** — confidence **high**.

## What the requirement demands

Every code path that closes a program account must send the reclaimed lamports to the
`["treasury"]` PDA — never to `Pool`, never to the admin, never to a caller-chosen account.

## Where enforcement lives

The program has exactly one account-closing path: the `Mapping` close in `fix_mapping`.

`program/programs/thugz-swap/src/instructions/fix_mapping.rs` L23–L29:

```rust
    #[account(
        mut,
        close = treasury,
        seeds = [MAP_SEED, pool.key().as_ref(), old_mint.as_ref()],
        bump = mapping.bump,
    )]
    pub mapping: Box<Account<'info, Mapping>>,
```

Anchor's `close = treasury` constraint transfers the closed account's entire lamport
balance to the named target, zeroes the data, and reassigns to the system program after
the handler returns (the file says so itself at L115–L116, and this is the documented
Anchor 1.1.2 `close` semantics — `anchor-lang = "1.1.2"` in
`program/programs/thugz-swap/Cargo.toml` L27).

The `treasury` target is not caller-arbitrary — it is pinned to the treasury PDA by seed
constraints, `fix_mapping.rs` L57–L58:

```rust
    #[account(mut, seeds = [TREASURY_SEED], bump = pool.treasury_bump)]
    pub treasury: SystemAccount<'info>,
```

`pool.treasury_bump` is the canonical bump, derived and stored at init
(`program/programs/thugz-swap/src/instructions/initialize_pool.rs` L42, L56:
`Pubkey::find_program_address(&[TREASURY_SEED], &crate::ID)` → `pool.treasury_bump`).
`SystemAccount` additionally enforces system ownership, matching the appendix's
"system-owned, zero data" treasury model.

## Paths walked

- `fix_mapping` (`fix_mapping.rs` L67–L120): the only instruction that closes an account.
  The close target is `treasury` by constraint; the handler itself does no lamport moves —
  the close happens in Anchor's post-handler exit code. Enforced.
- `swap`, `deposit_bird`, `recover`, `seal`, `set_paused`, `initialize_pool`: grep for
  `close|CloseAccount|close_account` across all of them returned nothing (see searches).
  No instruction closes `Pool`, the vault ATA, or any token account, so there is no other
  closed-account rent flow the requirement could apply to. `state.rs` L30 states the same
  intent: "the only close is" (fix_mapping's Mapping close).

## Why this verdict and not the adjacent ones

- Not **partial**: there is only one close path in the whole program, and it is enforced.
  Nothing closes to `Pool`, admin, or a caller account.
- Not **stronger-than-spec**: `close = treasury` is exactly what the appendix's "Closing in
  `fix_mapping`" section prescribes; nothing beyond it.
- The enforcement is declarative (an Anchor constraint), not a named check I could open —
  but the target account it names is itself constrained to the canonical treasury PDA
  (L57–L58), so the constraint cannot be redirected by the caller. That closes the
  "promising name, unverified body" gap: both halves (close semantics, target identity)
  are pinned in this file.

## Open questions

- The test's treasury-balance assertion (level1.rs L482) is a loose lower bound rather
  than an exact `mapping_rent − ata_rent` delta; it would still pass if the rent were
  burned rather than credited, though the mapping-zeroed assertions plus Anchor's close
  semantics make that combination implausible. A tightened exact-delta assertion would
  make the test airtight. This is a test-strength note, not a compliance gap in the
  program.
